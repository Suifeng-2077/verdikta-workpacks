Failure, explained

Every failed transaction on Solana already contains the answer: which instruction broke, which program refused it, whether your tokens moved, and what you paid anyway. The official explorer's summary card says one thing about it. This is the same page, saying the same facts in the order a person needs them.

Cause

The router JUP6…TaV4 refused its own instruction with custom error 6001 (0x1771). That number is defined by the program, not by Solana, so this page shows where to read it instead of guessing.

What usually changes the outcome A router rejecting its own instruction at this stage is normally the trade no longer matching the terms you set — the price moved before it landed. Retrying at the same size, or widening what you will accept, is the usual fix. Nothing was partially filled.

Design notes

  • Order is the whole feature. Verdict → did my money move → what did it cost → why → what next. The official explorer leads with a single badge, Program Error: "Instruction #5 Failed", which names the step and nothing else — not whether funds moved, not what the code means.
  • "Tokens moved: 0" is derived, not asserted. The transaction carries pre- and post-token balances; comparing them answers the only question a user actually has. On this transaction both sets are present and every one of the seven entries is byte-identical, so the panel can state "no token moved" rather than hoping it.
  • The step index is counted, not guessed. The message carries five top-level instructions; the router is the fifth and last one, which is why the panel says "step 5 of 5" instead of repeating the raw zero-based [4, …] from the RPC.
  • The error code stays, but it is demoted. 6001 is still printed, in monospace, next to a link to the program's own error table — because the code is real and a developer will want it. It is no longer the headline.
  • Receipt metaphor, not a dashboard. A failed transaction is a receipt for something that did not happen. Paper, a perforated edge, a stub with signature and slot: the form tells the user the transaction is closed and nothing is pending.
  • Mobile first, desktop identical. The same block goes to two columns above 900px; nothing is hidden, reordered, or turned into a horizontal scroll of a table.
  • Honest about what the data cannot say. The page never invents a reason for 6001. It states the mechanism (program-defined code), shows the evidence (instruction index, program id), and labels the guidance as "what usually changes the outcome".
